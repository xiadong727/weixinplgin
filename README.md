# 公众号一键排版

把 Markdown 一键排成符合微信公众号规范的图文。两种用法共用同一套排版内核：

- **浏览器扩展**：在公众号后台「新建图文消息」页面直接一键排版并插入正文
- **独立网页**：左边写 Markdown、右边所见即所得，复制后粘贴进后台

## 为什么要专门做这件事

公众号后台会剥掉 `<style>`、`class`、外链 CSS，只认元素上的 inline style。所以排版工具的核心是把
「Markdown → 带内联样式的 HTML」这条管线做扎实。这个项目的做法是渲染时直接输出 inline style，
不做后置 CSS 内联（不依赖 juice / cheerio），输出确定、预览与粘贴结果完全一致。

同时刻意避开了公众号会过滤的写法：`::before/::after`、`position`、负 margin、flex、CSS 变量、渐变、float。
所以所有装饰都做成真标签：标题序号、引用的大引号、分隔线纹样都是 `<span>`；任务列表用字符复选框
（`<input>` 会被剥掉）；项目符号改不了 `::marker`，就给 `li` 上主色再把内容包一层文字色；
首字放大用抬升的大号首字代替 `::first-letter`；代码高亮的每个 token 都带上 `color`。
有一条测试专门扫所有主题的输出，确保没有用到会被过滤的属性。

## 安装与使用

### 扩展

```bash
npm install
npm run build:ext
```

打开 Chrome `chrome://extensions` → 开启「开发者模式」→「加载已解压的扩展程序」→ 选 `dist/extension`。

然后进公众号后台的「新建图文消息」页面，右侧会出现绿色的「排版」条：

1. 点开面板，在「写作」里写 Markdown
2. 切「预览」看手机宽度下的效果，「设置」里调主题
3. 点「一键排版并插入正文」，确认无误后按微信自己的保存按钮
4. 万一自动插入失败，点「仅复制」再回正文手动粘贴

### 两种内容来源

面板底部的「内容来源」决定这次排版的内容从哪来：

- **面板里的 Markdown**（默认）：正文被排版结果整个替换。适合写完一篇直接发。
- **正文现有内容（只改样式）**：内容以左边正文为准，插件只把当前主题的样式套上去。
  适合你习惯直接在后台写字、只想调调样式的场景 —— 正文是内容的唯一来源，
  两边不会互相覆盖，也就没有「冲突」这回事了（这个模式下不会弹选择框）。

只改样式模式会先**清掉空白装饰块**：秀米、壹伴这类工具会在正文里留下一堆嵌套的空
`<section>` 做间距和装饰，平时看不见，一旦套上边框或底色就变成一格格空框。
清理规则见 `shouldDropWhenBlank`：空的 `<p>` 要留（很多人用空行调间距，
而段落不带边框、空着也不会显形），表格里的空单元格要留（那是表格结构的一部分），
其余空着的 `section` / `div` / `blockquote` / 列表一律删掉。

表格要单独处理，「跳过表格内部」这条规则会放过三样东西：

1. **一整张所有格子都空的表格** —— 套上单元格边框后就是一片空格子，
   而它未必有空的包裹层可以把它带走
2. **空的 `<caption>`** —— 它在表格**正上方**渲染成一条空白带，
   藏在 `<table>` 里面，最难发现的就是这个
3. **整行都空的 `<tr>`**，以及整块空的 `thead` / `tfoot`

`col` / `colgroup` / 空 `<span>` 这些不渲染，留着无害，不动它们。

**表格只输出 `table > tbody > tr > th|td` 这一种结构。**
公众号后台用的是 `prosemirror-tables`，它的表格 schema 只认这几层。多给
`caption` / `colgroup` / `thead` / `tfoot`，它消化不了就会把结构揉乱——
诊断里见过**表格被套进另一个表格的单元格里、正文内容跑进 `<tfoot>`** 的情况。

`caption` 尤其不能给：**它身上的 `style` 会被 schema 剥掉**。
我曾试过放一个 `display:none` 的隐藏 caption 去占位，结果样式被剥光，
一个赤裸的空 caption 就成了表格正上方那条虚线空带——等于自己把问题做了出来。

所以换样式时会把表格拍平：删掉 `caption` / `colgroup`，把 `thead` / `tfoot` 里的行
按原顺序并进 `tbody`（空行不并，否则会多出一条空带）。
有文字的 caption 转成表格前面的一个段落，内容不丢。

**保存草稿后编辑器还会再补。** 所以「清理空白格」是常驻能力：
实时同步开着时会自动盯着清（**不受「正文改动后自动套样式」那个开关影响**——
那个开关只管打字时要不要重排，保存后冒出来的空白格跟打字无关，不能被它连坐），
面板上也有一个**「清理空白格」**按钮，任何时候都能手动清。

**没有内联样式的「裸」容器会被中和。** 表格外面常有一层不带任何样式的 `<section>`，
它会吃到编辑器自己的 CSS（比如 `section:not([style])` 上的虚线边框），
在正文里表现为一个虚线空框。所以会给这类容器显式写上
`border:none; background-color:transparent; box-shadow:none`。
**有内联样式的不动**——那是用户自己的装饰容器，动了就破坏原有设计。

诊断报告里的「表格上方的结构」会逐层打印表格的外框和前方兄弟，
标出每个元素**有没有内联样式**、实际边框是什么。
这一条是用来区分「框是我们画的」还是「编辑器自己的界面辅助线」的——
两者的处理方式完全不同，光看标签统计分不出来。

自动清理的上限计的是「**连续清了还在**」的次数（3 次后停手并提示），
不是总次数——用户每次保存草稿都是独立操作，按总数封顶会让人存几次之后就再也不自动清了。
这个上限只用来防「编辑器立刻补回来」造成的无限对拉。

另外三条刻意的取舍，都是为了**反复换主题不会越换越脏**：

1. **标题按纯文字重建**。上一套主题留下的序号和符号混在文字里，不清掉就会
   `01` → `0101` → `010101`。我们自己加的装饰都带 `data-wxt-d` 标记，重建前按标记精确删除；
   标记万一被编辑器剥掉，还有一层符号/重复序号的兜底规则。
   代价是标题内部的加粗、链接等行内格式会被去掉。
2. **代码块按纯文字重新高亮**，语言自动识别。这样换代码配色能生效，也不会堆积旧的高亮 span。
3. **不做分隔线纹样、引用大引号、首字放大**，这几样在重复应用时无法可靠还原。

### 实时同步

面板底部有个「实时同步到正文」开关。打开之后，换主题、拖滑块、改 Markdown 都会自动刷新左边的正文，
不用每次点「一键排版并插入正文」。三条约束：

- **只在「替换全文」模式下可用**，插入到末尾模式会不断追加，没有意义
- **防抖 0.8 秒**。拖滑块时每动一下就重写一次正文，微信的撤销栈和自动保存都会被刷爆
- **「正文改动后自动套样式」默认关闭**，是个单独的开关。打开后你在正文里停手约 3 秒
  会整篇重排——写作时这很打断人，所以默认不开，需要时再勾。
  开着时整篇重写会把光标顶到文末，所以插入前会按「光标在纯文字里的第几个字」记下位置，
  重写后按同一个偏移找回去（换样式不改文字，这个偏移是稳的）。
- **重复插入的硬防护**：比的是「**这一次插入前后**」的字数。换样式本身绝不该改变文字，
  前后不等就一定是重复插入，此时立刻停掉同步并提示用「历史版本」回退。
  不能拿「开启同步时的字数」当基准——用户正常写新内容也会超，会误报停机。
- **容器去重保留文字最多的那个**，不是一律保留内层。新内容写在旧容器外面时外层才是全的，
  留内层会把新写的段落整个丢掉；被保留者里面套着的旧壳则拆掉壳、内容留下，避免一层层套下去。
- **只改样式模式下不做「已是最新就跳过」的优化**。这个模式的内容本来就是从正文读的，
  文字永远相等，跳过判断恒成立 —— 新加的段落会永远套不上样式。
- **正文被手动改过时，方向交给你定**（这条只对「面板 Markdown」模式）。同步是单向的（面板 → 正文），但正文可以手动编辑。
  开着实时同步时每 1.5 秒对一次文字指纹，发现被手动改过就**立刻**弹出选择框并暂停同步：
  「以正文为准」保留改动并停掉同步，「以面板为准」覆盖正文并继续。
  在你做决定之前，改任何设置都不会动正文。

  （没有做「正文改动反向同步回面板」：面板里是 Markdown，正文是富文本，
  反向转换必然有损，主题装饰会变成垃圾字符再被重新排版，越滚越乱。）
- **不怕微信改写 HTML**。微信粘贴后会自己规整一遍（补 data-*、重写 style），
  所以「有没有被手动改过」的判断只比对**文字指纹**，不比对 innerHTML，
  否则第二次同步就会被误判成用户编辑过而停掉
- **等正文真的变了再判成功**。原先固定等 150ms，长文里微信还没处理完就被判定失败，
  于是又用 execCommand 插了第二遍，会重复插入。现在改成轮询到内容稳定
- **阅读位置保持不变**。微信的粘贴处理器插完会把光标收到文末，浏览器随即把光标滚进可视区，
  于是每同步一次正文就跳到最后。所以同步前会记下视口顶部那一段的文字内容和它距顶的偏移，
  重排后按**文字**（不是序号，换主题时结构会变）找回同一段，把它放回原位；
  光标引起的滚动不一定在同一帧发生，因此随后几帧会持续校正到稳定

因为它会占用微信的撤销记录，开启时有一次确认，建议在草稿上用。

### 找不对正文区会怎样

公众号后台的标题、摘要也是 contenteditable，页面里还可能有别的 iframe。
选错目标的表现是「提示已同步，但正文一点没变」——内容其实写进了别的框。
所以正文区是**在所有同源 iframe 和主文档里收集全部可编辑区域，再按高度和面积择优**，
而不是命中第一个就用。

判断元素时不能用 `el instanceof HTMLElement`：iframe 里的元素属于 iframe 自己的 window，
和主页面的 `HTMLElement` 不是同一个构造函数，这个判断恒为 false，会把真正的正文区整个滤掉。

插入之后会立刻回读确认，并在后台再盯 2.5 秒——编辑器按自己的模型重渲染是异步的，
可能几百毫秒后才把正文换回上一版（**文字一样、样式回退**，就是「闪一下又变回去」）。
盯到被还原就自动补插一次，补不回来才报错。阻塞等这么久会让每次同步都慢一两秒，所以放后台。这里**不能直接比字符串**：
我们输出时把 `"` 转义成了 `&quot;`，而从 DOM 读回来的文本里是原字符，
正文里但凡早早出现一个引号，比对就会失败、把成功的插入误判成失败。
所以比对走 `core/compare.ts`：先去标签解实体，再从开头/中间/结尾抽样比对，
容忍微信剥掉部分装饰，但内容被整个换掉时一定判否。

**最硬的依据是主题主色**：插入时会把当前主题的主色一并传进去，
「正文是不是已经是这套样式」必须先满足主色真的出现在正文里（`#1F4E79` 和
`rgb(31, 78, 121)` 两种写法都认）。少了这一条，颜色频次指纹会误判，
一旦误判就会整个跳过插入却报「正文已是最新」，样式永远不更新。

而且「无需插入」的判定比「插入成功」严格得多：判成功错了顶多多插一次，
判「已是最新」错了就是彻底不动。

**只比文字还不够**：编辑器可能重渲染回同一篇文章的上一套样式，文字完全一致。
所以还要比「样式指纹」——从 HTML 里挑出现最多的几个颜色值，要求主色必须在、且过半命中。
挑颜色时会先剔掉代码块：不同主题常共用同一套代码高亮配色，算进去会让两套完全不同的主题
互相命中，误判成「已经是这套样式了」。

另外判断插入成功不看「innerHTML 有没有变化」，而是直接问「正文现在是不是我要的那篇」。
前者在「要插入的内容和已有内容一样」时会误判成失败，白等一个超时再降级到下一个通道；
现在这种情况直接跳过插入，既省掉一次全文重写，也不会平白污染撤销栈。有些编辑器是受控组件，
外部写进 DOM 的东西会被它按自己的数据模型重渲染掉——这种「假成功」会如实报错，
而不是继续报「已同步」空转。

面板里的**「诊断」**按钮会把页面上所有可编辑区域、选中的是哪个、尺寸、内容长度
打成一份报告复制到剪贴板（控制台也打印一份），排查上面这些问题时直接发出来即可。

### 后台用的是 ProseMirror

公众号后台的正文区现在是 `div.ProseMirror`（受控组件，按自己的文档模型渲染），
不再是老的 UEditor iframe。两件事因此必须特别处理：

**全选要走编辑器自己的命令通道。** 受控编辑器维护自己的选区模型，手工造的 `Range`
它不一定认，「全选」就变成了「没选中」，粘贴于是退化成追加。所以替换全文时先试
`execCommand('selectAll')`，失败才退回手工 Range。

**全选要确认真的选住了正文。** `execCommand('selectAll')` 在焦点没落进编辑器时会选中整个页面，
range 非空但根本不是正文 —— 粘贴就变成了追加。所以会检查选区是否落在正文区内、
且覆盖了它九成以上的文字，不满足就退回手工 Range。

**替换全文要先真的清空。** 不能指望粘贴会替换选区：先全选再 `execCommand('delete')`，
删不掉就直接清 DOM。少了这一步，正文每同步一次就完整追加一份 ——
实测 18 次同步能把 5 千字的稿子堆到 10 万字，直接触发后台的「自动保存失败」。

**体积兜底。** 编辑器会剥掉我们自己打的 `data-tool` 标记，靠标记计数会失灵，
所以还要比纯文字长度：正文比该有的长 40% 以上就清空重插。

**字体不能只写在最外层容器上。** 靠继承的属性（font-family）只挂容器时，
「只改样式」模式取的是 `innerHTML`，容器自己的 style 正好被丢在外面，
表现就是「改字体没反应」。所以容器必须是 `innerHTML` 里的一个真实 `<section>`，
同时字体也要落到段落、列表、表格这些文字元素上（编辑器可能给子元素设了自己的 font-family）。

**判「要不要跳过」和判「插入成功没有」，严格程度必须不同。**
换字体、字号、行高时一个字都不会变、主题色也不变，所以「跳过」的判断必须带上
样式片段（`font-size:16px`、`line-height:1.75`），否则改了等于没改。
但**「成功」的判断绝不能带样式片段**：浏览器会把 `margin:0 0 20px` 规范成
`0px 0px 20px`、给字体名加引号，片段对不上就会把成功的插入判成失败，三级通道全废。
前者判错顶多多插一次，后者判错就是彻底不能用。

**「已是最新就不插」这个优化要判得极严**：文字必须一模一样才跳过。
留哪怕 5% 的容差都不行——手打几个字占全文的比例本来就很小，
一旦被当成「已是最新」，用户选了「以面板为准」也覆盖不掉。
用户明确要求覆盖时还有 `force` 通道，直接跳过这个优化。

**全选后的选区可能落在已有容器内部**，新的排版容器会套进旧容器里：正文每同步一次就多一层壳，
外层的字体和颜色还会串到内层。所以插入后会检查 `[data-tool="wx-typeset"]` 的个数，
多于一个就只保留最后插入的那个（嵌套的用内层顶替外层，并列的直接删掉）。

**后台盯梢要带代号。** 每次插入都有一个递增的代号，盯梢任务只在自己仍是「最新那次」时才动手。
少了这个判断，换主题时上一次的盯梢会发现「我负责的那版内容不见了」，
把**旧主题**的内容又插一遍。

**插入是怎么做的**：微信的正文是 UEditor 系的 `iframe + contenteditable`，直接改 `innerHTML`
会绕过它的变更追踪导致自动保存不触发。所以插入分三级降级：

1. 构造合成 `paste` 事件（带 `text/html` 的 DataTransfer），让微信自己的粘贴处理器接管 —— 等价于程序化的手动粘贴，兼容性和手贴一致
2. `execCommand('insertHTML')` —— 仍走浏览器编辑命令，会触发 `input` 事件
3. 直接写 `innerHTML` —— 最后手段，此时会提示你在正文里随便敲一下触发保存

三级都失败就退回剪贴板。微信改版时最多降级，不会彻底不可用。

### 网页版

最省事的用法是打成单文件，之后双击就能用、可以随便拷走：

```bash
npm install
npm run build:single    # → dist/公众号一键排版.html，双击打开即可
```

注意单文件是 `file://` 打开的，浏览器不一定给本地存储，设置和草稿可能记不住。
想让它记住就用本地服务：

```bash
npm run preview   # 构建产物起服务，http://localhost:5273
npm run dev       # 开发模式（改代码热更新）
npm run build     # 只出 dist/web，交给任意静态服务器托管
```

快捷键 `Cmd/Ctrl+Shift+C` 直接排版并复制，支持导出 HTML。

### 导入本地 Markdown

网页版点右上角绿色的「导入 .md」，或者直接把文件拖到编辑区；扩展面板里点「导入 .md」，
或者把文件拖到面板上。编辑区为空时会显示一块虚线引导，免得这个入口被忽略。
支持 `.md` / `.markdown` / `.mdown` / `.mkd` / `.txt`，上限 2 MB。导入时会自动处理这几件事：

- **编码**：先按严格 UTF-8 解，失败就退到 GB18030。从 Windows 传过来的中文 `.md` 常常是 GBK，
  直接按 UTF-8 读会整篇乱码，这里会识别出来并提示你最好另存为 UTF-8。BOM 和 UTF-16 也认。
- **front matter**：Hexo / Hugo / Obsidian 开头那段 `---` 包起来的元数据会被剥掉，
  不会当成正文渲染出来；如果里面有 `title` 而正文又没有 H1，会把它补成大标题。
  正文中间的 `---` 分隔线不受影响。
- **换行**：CRLF 统一成 LF。
- **本地图片**：`![](./img/a.png)` 和 Obsidian 的 `![[a.png]]` 都会被点名，
  因为公众号抓不到本地文件，必须先传图床再换成 http(s) 链接。

一次只排一篇，选了多个文件只会用第一个。

## 分享给别人

```bash
npm run pack
```

产物在 `dist/share/`，四个文件：

| 文件 | 给谁 |
|---|---|
| `wx-typeset-extension-v2.0.0.zip` | 想要「在后台里直接排版」体验的人，解压后按 README 装 |
| `公众号一键排版.html` | 不想折腾扩展的人，双击就能用，写完复制粘贴到后台 |
| `主题对照.html` | 挑主题用，一页看完全部效果 |
| `先看我.txt` | 安装和使用说明 |

压缩包内部一律用 ASCII 文件名：中文名在 Windows 自带解压里经常变乱码，
而那个文件夹是要在 Chrome 里选中的，名字乱了就没法操作。

三条分发路线的取舍：

- **发压缩包**：零成本，但对方要开「开发者模式」，Chrome 每次启动会弹一次提示（点取消即可），
  而且**不会自动更新**——你改了版本得重新发一份
- **上架 Chrome 应用商店**：对方一键安装、自动更新、没有开发者模式提示。
  需要 5 美元一次性开发者注册费、准备隐私政策，审核几天
- **只发网页版**：最省事，双击即用，或者把 `dist/web` 丢到任意静态托管（GitHub Pages / Vercel / Cloudflare Pages）给个链接

## 已知边界

- 图片需要是可公网访问的 http(s) 链接，微信在粘贴时会自己抓取转存；本地路径会被提示
- 没做图床上传（不想引入账号体系），需要图床的话自行上传后引用链接
- 「已有富文本一键美化」暂未实现，目前只吃 Markdown
- 避免行尾孤字需要按实际字体测量宽度，内联样式做不到，因此没有实现
